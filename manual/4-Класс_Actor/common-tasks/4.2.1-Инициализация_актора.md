Периодически требуется произвести какие-то действия — например, установку переменных, или выдачу инвентаря, или предпроверки — перед появлением актора в мире.

!!! note "Переменные посредством инвентаря — зло"
	В ZScript лучше избегать использования, как принято в Decorate, предметов инвентаря в качестве переменных, если такая система не завязана на какие-либо соглашения (например, если не требуется совместимость с уже написанным Decorate-кодом или другими акторами, проверяющими инвентарь). При создании нового предмета инвентаря инициализируется полноценный актор, а это сотни параметров и десятки проверок; при поиске/изменении предмета ситуация немного лучше, но в любом случае это явная потеря производительности на пустом месте.


### Последовательность действий движка при создании актора {#что-происходит-при-создании-актора}

1. Внутреннее конструирование актора (выделение памяти, добавление в списки движка);
2. Инициализация всех значений из блока `Default`;
3. Инициализация базовых полей актора, вроде позиции в мире и указателей на спрайты;
4. Вызов [функции `BeginPlay()` — см. ниже](#beginplay);
5. Инициализация других флагов, обновление переменных вроде `level.total_items`;
6. (...Ожидание начала следующего глобального игрового такта...);
7. Вызов [функции `PostBeginPlay()` — см. ниже](#postbeginplay);
8. Посылка [события `WorldThingSpawned()` с указателем на этот актор — см. ниже](#eventhandler-worldthingspawned) _(традиционно считается единственно правильным местом, где можно вмешаться в создание актора, не изменяя чужого кода)_;
9. Актор готов для своего первого `Tick()`!

Наиболее часто используемый способ — переопределение функции `PostBeginPlay()`.


## Функция `PostBeginPlay()` {#postbeginplay}

Актор вызывает функцию `PostBeginPlay()` прямо перед передачей события `WorldThingSpawned()` и сразу затем первым своим `Tick()`. Другими словами, эта функция может инициализировать актора как для `WorldThingSpawned()`, так и для `Tick()`, не опасаясь, что между ними вызовется что-то ещё.

```CPP
class MyActorPostBeginPlayInit: DoomImp {
	override void PostBeginPlay() {
		// Какие-нибудь действия...
		health = int( round( health * FRandom( 0.5, 1.0 ) ) );
		A_GiveInventory( "Clip", 5 );

		// Продолжение `PostBeginPlay()` по умолчанию.
		Super.PostBeginPlay();
	}
}
```


### Если упустить вызов `Super.PostBeginPlay()` {#без-super-postbeginplay}

Поведение соответствует стандартному для виртуальной функции. Так что:

- Функция родительского класса `PostBeginPlay()` (если она переопределена) не будет вызвана.
- Когда переопределений не было вплоть до класса `Actor`, то не сработает `NoDelay` в стейтах и динамический свет может появиться с задержкой в такт. То есть ничего страшного, но, чтобы не было неожиданностей даже в редких случаях, лучше вызов `Super.PostBeginPlay()` всегда оставлять.

??? question "Подробности и пример..."
	#### Подробности: что функция делает по умолчанию {#без-super-postbeginplay-подробности}
	Упрощённо говоря, функция `PostBeginPlay()` в `Actor` имеет следующие вызовы:
	```CPP
	override void PostBeginPlay( void ) {
		// Привязывание динлайтов из GLDEFS:
		LinkGLDEFSDynamicLights();
	
		// Проверка на `NoDelay` в первом стейте:
		CheckNoDelay();
	}
	```
	
	- Первая часть, которую можно назвать `LinkGLDEFSDynamicLights()`, отвечает за мгновенное привязывание к актору динамического света из [lump GLDEFS](https://zdoom.org/wiki/GLDEFS). Без него свет привяжется со следующего игрового такта, что может быть заметно, если какой-нибудь факел будет стоять в начале уровня прямо напротив игрока. Кстати, если привязывать свет напрямую к стейту через `Light( "..." )`, такой проблемы не будет.
	
	- Вторая часть, `CheckNoDelay()`, отвечает за принудительный вызов функций-кодпоинтеров в стейтах, помеченных как `NoDelay`. С учётом того, что при этом переопределена сама `PostBeginPlay()`, в которой и следует делать инициализацию, обычно это совсем не критично.
	
	Соответственный объединяющий всё это пример, где актор поведёт себя слегка некорректно. Надпись не выведется, и динамический свет появится с микроскопической задержкой:
	```CPP
	/* === ZScript === */
	
	class ActorNoPBPTest: BlueTorch {
		override void PostBeginPlay() {
			//Super.PostBeginPlay();
		}
	
		States {
		Spawn:
			TBLU A 0 NoDelay A_Log( GetClassName() .. "'s NoDelay" );
		SpawnLoop:
			TBLU ABCD 4 Bright;
			Loop;
		}
	}
	```
	```CPP
	/* === GLDEFS === */
	
	object ActorNoPBPTest {
	    frame TBLU { light BIGBLUETORCH }
	}
	```
	В консоли перед `summon ActorNoPBPTest` можно набрать `i_timescale 0.2`.


!!! note "Примечание"
	Этот метод унаследован от `Thinker::PostBeginPlay()`. Формально говоря, в самом `Thinker` тело метода пустое, так что при наследовании от него, а не от `Actor`, не прописывать `Super.PostBeginPlay()` безопасно и корректно.


## Функция `BeginPlay()` {#beginplay}

На момент вызова `BeginPlay()` актор инициализировался ещё не до конца, и в этот момент опираться можно только на базовые характеристики: всё из блока `Default {}`, позиция X/Y/Z, сектор, стейт, спрайт, фрейм спрайта, установленная тактвая задержка до смены стейта, некоторые принудительно исправленные флаги, а также некоторые свойства вроде `WaterLevel` и переменной корня диалога из Strife.

```CPP
class MyActorBeginPlayInit: DoomImp {
	override void BeginPlay() {
		// Какие-нибудь действия...
		health = int( round( health * FRandom( 0.5, 1.0 ) ) );
		A_GiveInventory( "Clip", 5 );

		// Но: например, удаление актора из счётчиков уровня kills/items приведёт
		// к сбою в счёте, так как этот актор ещё не был в них учтён!
		//ClearCounters();

		// Продолжение `BeginPlay()` по умолчанию.
		Super.BeginPlay();
	}
}
```

В целом, если есть возможность использовать `PostBeginPlay()`, безопаснее использовать его.


### Если упустить вызов `Super.BeginPlay()` {#без-super-beginplay}

Поведение соответствует стандартному для виртуальной функции. Так что:

- Функция родительского класса `BeginPlay()` (если она переопределена) не будет вызвана.
- Когда переопределений не было вплоть до класса `Actor`, то не будет работать флаг `+DORMANT`.

По умолчанию `BeginPlay()` при наличии флага `+DORMANT` вызывает деактивацию актора и тут же снимает этот флаг:
```CPP
virtual void BeginPlay( void ) {
	if ( bDORMANT ) {
		Deactivate();
		bDORMANT = false;
	}
}
```

## Инициализация в `Tick()` {#tick}

Из очевидных минусов — такая инициализация будет давать дополнительные расходы производительности каждый такт, пусть и небольшие.
```CPP
class MyActorTickInit: DoomImp {
	bool initialized;

	override void Tick() {
		if ( !initialized ) {
			// Какие-нибудь действия...
			health = int( round( health * FRandom( 0.5, 1.0 ) ) );
			A_GiveInventory( "Clip", 5 );

			// Установка флага успешной инициализации.
			initialized = true;
		}

		Super.Tick();
	}
}
```


## Инициализация в последовательности стейтов `Spawn:` {#spawn-state}

Сопряжено с необходимостью помнить особенности работы стейт-машины. В случае с простыми акторами — условно говоря, декорациями — подводных камней, не считая косых взглядов, особо нет:
```CPP
class MyActorSpawnState1Init: Actor {
	States {
	Spawn:
		TLMP A 0 NoDelay A_SpawnItemEx( "ExtraActor1" );
		TLMP A 0 A_SpawnItemEx( "ExtraActor2" );
		TLMP A 0 A_Log( GetClassName() .. " initialized." );
	SpawnLoop:
		TLMP ABCD 4 Bright;
		Loop;
	}
}
```

А вот в случае с самостоятельным актором, к примеру, монстром, всё становится сложнее.
