Структура данных (не путать со `struct`) — вспомогательная абстракция над хранением данных, которая позволяет эффективнее искать, добавлять, удалять, перебирать и обращаться напрямую к элементам.

Понятие структуры данных часто идёт рука об руку с алгоритмами, и их грамотное объединение может давать огромный прирост в скорости работы программы.

!!! tip "Проще говоря"
	Структура данных — удобный способ хранить данные, оптимизированный под некоторые частые операции.


### Нотация временнóй сложности структур данных {#нотация-временной-сложности}

Не бывает универсальных структур данных, и чем-то в любом случае придётся платить. Так, какие-то структуры производят сверхбыстрый поиск по миллионам элементов, но при добавлении/удалении элемента могут требовать значительных затрат вычислительной мощности; какие-то могут мгновенно добавить или удалить элемент из любого места, но чтобы обратиться к нужному месту, придётся перебрать всё. Простейшим примером является _массив_, в котором обращение по индексу происходит мгновенно, но поиск элемента может затянуться, если элемент окажется в самом конце.

Обобщённая зависимость длительности обработки при исполнении действия от количества элементов называется _временнóй сложностью_, в англоязычных источниках "time complexity".

!!! tip "Проще говоря"
	Временнáя сложность — насколько сильно тормозит структура данных на основных операциях, если элементов ОЧЕНЬ много.

Для структур данных выделяют _наилучшую_, _усреднённую_ и _наихудшую_ временную сложность для всех основных действий: прямого доступа, поиска и добавления/удаления элемента. Обычно имеет смысл смотреть только на сложность в худшем случае, так как она обязательно породит тормоза прямо во время работы программы (во время игры).

Худшая временная сложность обозначается буквой `O(…)`, где на месте `…` стоит формула-зависимость от числа элементов `n`. Например, простой перебор всего массива имеет сложность `O(n)`, так как все элементы массива нужно посетить ровно один раз.

Примеры:

- `O(1)`. Наилучшая сложность, так называемая "постоянная сложность" — это если операция со структурой данных производится за одинаковое время вне зависимости от количества элементов. То есть здесь время работы не зависит от того, сколько данных сейчас содержит структура, три, двести или миллиард.
- `O(n)`. Средняя сложность — когда для достижения цели каждый элемент требуется получить хотя бы один раз.
- `O(log(n))`. Хорошая сложность — логарифмическая, то есть для вполнения операции нужно посетить не более чем логарифм от числа элементов (а это действительно мало, `log₂(1'000'000) ≈ 20` — двоичный логарифм от миллиона примерно равен двадцати, т. е. миллион элементов обработаются всего за 20 шагов). Обычно используется логарифм по основанию 2.
- `O(n²)`. Ужасная квадратичная сложность. Чтобы достичь цели, при ней требуется посетить все элементы как минимум столько же раз, сколько есть этих элементов. То есть, если их 100, будет 10'000 шагов.

## Массив {array}

Как упоминалось в [3.2.6. Массивы](../3-Синтаксис_и_семантика/3.2-Основы_синтаксиса_кода/3.2.6-Массивы_и_структуры_данных.md),

> Массив — это последовательность однородных элементов. ZScript предоставляет два встроенных вида массивов: статический (ограниченный, под который память выделяется заранее) и динамический.

В силу своей простоты и понятности это самая часто используемая структура данных в модах на ZScript.

### Эффективность и временная сложность массива {array-эффективность}

Временная сложность массива в наихудшем случае:

- `O(n)` для поиска (нужно перебрать все элементы до нужного, а он может быть в конце).
- `O(n)` для добавления/удаления (нужно сдвинуть все последующие элементы, и плохо, если изменение в начале).
- `O(1)` для доступа по индексу, здесь массиву нет равных.

При добавлении элемента в динамический массив, если у него закончилось выделенное место, всё его содержимое перемещается в более длинное свободное место в памяти. При очень большом количестве элементов может пару раз за игру вызвать ухудшение производительности.


## Связный список (Linked list) {#linkedlist}

Связные списки — структура данных, в которой каждый элемент соединён с соседями (есть указатель на следующий и предыдущий).

По односвязным спискам можно продвигаться только вперёд, к следующему элементу (у них не существует поля "предыдущий элемент"). Их обобщённое описание выглядит так:
```CPP
class SinglyLinkedList {
	SinglyLinkedListNode head;   // Первый элемент списка.
	//SinglyLinkedListNode tail; // Последний элемент списка (в односвязном
	                             //списке в принципе можно обойтись и без него).
}

class SinglyLinkedListNode {
	Data data;                 // Данные, которые нам нужно хранить.
	SinglyLinkedListNode next; // Следующий элемент списка.
}
```

В двусвязных списках в каждом элементе есть ещё и указатель `prev`:
```CPP
class DoublyLinkedList {
	DoublyLinkedListNode head; // Первый элемент списка.
	DoublyLinkedListNode tail; // Последний элемент списка.
}

class DoublyLinkedListNode {
	Data data;                 // Данные, которые нам нужно хранить.
	DoublyLinkedListNode next; // Следующий элемент списка.
	DoublyLinkedListNode prev; // Предыдущий элемент списка.
}
```

### Как хранится инвентарь актора {#linkedlist-инвентарь-актора}

Инвентарь игрока (и любого другого актора) работает именно что по принципу односвязного списка. У каждого класса актора — в том числе и у класса `Inventory` — есть поле-указатель `Inventory inv`. Таким образом:

- Актор-владелец в этом поле хранит указатель на свой первый предмет инвентаря.
- Первый предмет хранит в этом поле указатель на второй предмет инвентаря (или `NULL`, если его нет).
- Второй предмет хранит в этом поле указатель на третий предмет инвентаря (или `NULL`, если его нет).
- Третий предмет... (И так до тех пор, пока не встретится `NULL`).

Полный цикл перебора:

```CPP
// Первый предмет берётся с актора `mobj`:
Inventory curinv = mobj.inv;

// Каждый следующий предмет берётся с предыдущего:
while ( curinv = curinv.inv ) {
	// Что-нибудь делаем с инвентарём.
	console.printf( "Предмет %s, количество %i", curinv.GetClassName(), curinv.amount );
}
```

Обобщённый вид прохода по односвязному списку:
```CPP
class LinkedListNode {
	Data data;  // Данные, которые нам нужно хранить.
	LinkedListNode next;  // Следующий элемент списка.
}


/* while-вариант */

LinkedListNode node = GetNode();

while ( node = node.next ) {
	// Если в `node.next` (и, как следствие, просто в `node`) окажется NULL, 
	//while() выйдет из цикла.

	// Действие...
}


/* for-вариант */

for ( LinkedListNode node = GetNode(); node != NULL; node = node.next ) {
	// Действие...
}
```

### Эффективность и временная сложность связного списка {#linkedlist-эффективность}

Проблема связных список в том, что у них происходит огромное количество разыменований указателя. Буквально каждый переход дальше или назад — это получение новой структуры по адресу.

В GZDoom он быстрее динамических массивов только на очень малых (примерно до десяти элементов, варьируется в зависимости от архитектуры компьютера).

### Как хранятся строки для локализации {#hashmap-внутри-stringtable}

Файлы `LANGUAGE` задают формат, до ужаса напоминающий хэш-таблицу: идентификатор строки, как `GOTARMOR` для сообщения о подборе зелёной брони в Doom, и связанное с ним значение, как "Picked up the armor".

Возьмём простую выдержку из PK3 со старым форматом задания текстовых строк. _Для нового формата внутри движка происходит то же самое, но демонстрировать его неудобнее_.
```ini
SECRETMESSAGE = "A secret is revealed!";

PRESSKEY = "Press a key.";
PRESSYN = "Press y or n.";

QUITMSG = "Are you sure you want to\nquit this great game?";
TXT_YES = "Yes";
TXT_NO = "No";
```
Фактически здесь в качестве ключа выступает одна строка (например, идентификатор `PRESSYN`), в качестве значения — другая (для выбранного ключа будет "Press y or n.").

Отличным примером использования такой реализации таблицы локализации является старый и известный [мод Footsteps от Zombiekiller](https://forum.zdoom.org/viewtopic.php?t=35388), в котором в качестве ключа задаётся название текстуры, в качестве значение — название воспроизводимого звука шага. Таким образом получается мгновенный поиск соответствия силами движка.

### Эффективность и временная сложность хэш-таблицы {#hashmap-эффективность}

Временная сложность в среднем случае:

- Амортизированная `O(1)` для поиска (в общем случае хэш считается мгновенно).
- `O(1)` для добавления/удаления (нужно сдвинуть все последующие элементы, и плохо, если изменение в начале).
- Доступа по индексу не существует. Для полного перебора нужно пройтись по всем ячейкам таблицы, даже пустым.

Временная сложность в наихудшем случае:

- `O(n)` для поиска, добавления и удаления (придётся пройти всю цепочку, если все элементы свалились в одну).
- Справедливости ради, при хорошей хэш-функции даже подобрать такой случай трудно.
